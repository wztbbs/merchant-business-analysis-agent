# 固定 DAG、动态 ReAct 与后续设计边界

本文件已按当前实现修订。旧版“尚未接入动态执行”的判断已不适用，但目前仍没有实现模型生成/修改完整 DAG 的通用规划器。

## 当前已实现的两种执行形态

1. **固定 DAG**：Playbook 在执行前展开完整节点、依赖、参数和逻辑供给。PlanValidator 校验后，ExecutionService 按拓扑层执行；证伪可以跳过既有因子后续步骤，不会临时新增节点。
2. **动态串行工具循环**：ReAct 每轮决定加载、调用、检查或结束。下一次动作可根据已取得事实变化；记录是调用轨迹，不是执行前生成的 DAG。每次调用和最终覆盖度由代码校验。

因此“有动态执行”与“有动态 DAG 计划语言”不是同一件事。ReAct 空 Plan 标记不表示工作流丢失，真实状态在 react_run/react_event/step_run。

## 当前没有实现的功能

- 模型一次生成任意 Plan，校验后作为新 DAG 执行。
- Playbook 执行一半自动转 ReAct、由模型删除/追加原 DAG 节点。
- ReAct 同一动作并行调用多个工具、自动推导并发子图。
- 任意条件分支、循环节点或表达式执行语言。
- LangGraph 等外部编排框架、分布式锁、精确一次外部执行。

现有问题覆盖通过“识别阶段先选路由”扩展，不是把原有固定执行器改造成任意动态图引擎。

## 已复用的基础能力

统一轻量工具目录、按需 Schema、结构化数据引用、冻结时间、不可变调用快照、业务/计算分层、步骤结果、历史快照和预算状态，均可继续支撑更复杂编排。不能由此宣称已有完整量纲证明、跨数据源数据就绪校验或自动因果推断。

当前 ReAct 的停止规则和恢复详见[ReAct](react.md)，固定 DAG 的例子见[执行](execution.md)。模板之外的长尾可以被尝试，但没有数据/工具的需求依然需要明确能力不足。

## 如果以后新增动态 DAG

以下是后续设计要求，尚未作为功能实现：

1. 为计划语言定义清晰的节点、分支、产出和修改边界，不能只靠自由文本。
2. 每次图变更校验依赖、供给、预算与历史事实可复用性；不可失去现有引用与冻结时间约束。
3. 区分可重试只读工具和有副作用工具，设计幂等与恢复语义。
4. 明确并发调用如何提交结果、部分失败如何影响需求完成度和回答。
5. 对新增能力做真实模型和运行质量评测，再决定是否值得增加编排复杂度。

工具数量 50 或某个固定场景数不是必须升级为动态 DAG 的硬阈值。是否升级应基于真实长尾任务形态、工具链、可维护性与效果数据。
