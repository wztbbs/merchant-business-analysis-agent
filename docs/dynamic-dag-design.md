# 动态 DAG：取舍与未来接入方案

先澄清一个常见误解：**我们的 plan 本身就是 DAG**（有向无环图，即"步骤之间有依赖、依赖不成环"
的执行图）。每个节点声明"我等谁"（depends_on），执行器据此分批跑。所以真正的分歧不是
"用不用 DAG"，而是：**图的形状是执行前就定死，还是运行时可以改**。

LangGraph 这类框架卖的是后者：跑到一半可以临时加步骤、删步骤、换路线，甚至让 LLM 当场决定
"下一步去哪"。好比导航软件：我们的方案是出发前把全程路线打印出来，逐路口核对没问题才发车；
动态 DAG 是边开边决定，每个路口问一次 LLM"往哪拐"。

注意区分范式和框架：下面讨论的是"运行时可改图"这个**范式**的取舍；断点存档、执行轨迹可视化
这类现成设施是 LangGraph 这个**具体框架**的工程红利——自己实现动态 DAG 范式并不会自动获得
它们（我们现在用 SQLite 表自己实现了一份简版）。

## 1. 动态 DAG 能带来什么

1. **收窄"暂不支持"的边界**：从"没有模板就不答"收窄到"没有能力才不答"。现在被挡在门外的
   query 分两类：一类是能力根本不存在（"复购率"没有对应的查询能力，该补数据补数据）；
   另一类是**能力都在、只是没有现成模板**（跨场景组合、非常规问法）。动态 DAG 能接住后一类。
   而且它和 bad_query_case 机制形成正循环：动态图兜底的 query 照样落库统计，兜底成功率高的
   问法固化成新模板，模板覆盖率越来越大，动态图退守长尾。
2. **假设被推翻后自动换思路**。现在用户问"是不是下架导致的"，查下来没有下架记录，系统会标记
   "用户假设不成立"、只跳过下架模块自己的后续步骤，其他因子照常排查。分场景看：诊断场景里默认
   原因（活动/流量/价格/缺货）本来就并行挂载，假设证伪后结论仍能交代真实原因（"不是下架，是
   流量和转化"）——相当于靠预挂默认因子部分实现了换思路；但因子影响评估场景没有默认因子，
   假设一证伪就只剩"不是下架"。动态 DAG 可以更进一步——当场换假设接着查："不是下架？那贡献最大
   的单品发生了什么，我再去查"。现在这需要用户换个问法重新提问，动态图能自己接得住。
3. **一层层往下钻的问题**。"销售额为什么跌"→"主要是无糖可乐跌"→"无糖可乐为什么跌"→"因为它
   下架了"——这种追问要钻几层，提问时不知道，模板没法提前写死层数；动态图可以查到哪钻到哪。
4. **一句话里问了好几件事**。"销售额为什么跌，顺便把本月报表给我"——跨了两个场景，我们现在
   只能挑一个主场景答；动态图可以把两支流程拼起来都跑。

## 2. 它解决不了什么

上面第 1 条说的是"能力都在、只是没模板"的那部分。但 bad_query_case 里还有另一类答不了的问题
（"复购率怎么样"、"库存够卖几天"、"新客老客占比"），**它们不缺"灵活的编排"，缺的是数据本身**。
"复购率"答不了，是因为数据库里根本没有算复购率的那段 SQL、那个查询能力——这就好比给了厨师
一本可以临场自由发挥的菜谱，但厨房里根本没有那道菜的原料。动态 DAG 解决的是"已有的食材怎么
组合"，而这类问题缺的是食材。所以它们正确的归宿是现在的机制：落库、聚合统计、看哪类需求频次
高，然后**正经为它补数据、补查询能力、做成新模板**——而不是用动态图生成一个低可靠的回答。

## 3. 为什么当前阶段不用

采用动态 DAG 的代价：

1. **校验从执行前变成执行中或执行后**。现在 plan 生成后、执行前，校验器能拦下所有结构错误
   （引用了不存在的查询能力、依赖成环死锁、等的上游数据根本没人产出），拦不住就不碰数据库。
   路线边开边定之后，校验只能跟在后面追，"少跑了一步"这种错在事后最难发现——商家看到的结论
   缺了一块，但每一句读起来都挺像真的。
2. **数字传递更容易被 LLM 影响**。经营分析的结论全是数字，而数字在节点间的传递（"整体跌了
   10 万"要当作下一步算贡献率的分母）现在是代码直接传递，不经过 LLM。LLM 参与路线决策后，
   数字得放进对话里让它记住再填回来——它可能四舍五入、可能把 A 节点的数填到 B 节点，
   不报错，只是安静地算错。
3. **LLM 调用次数增加，成本和延迟更高**。我们现在问一次固定只调 2 次 LLM（开头理解问题、
   结尾写结论），中间全是毫秒级的 SQL。动态图每个路口都要问一次 LLM，调用次数翻好几倍，
   商家等结论的时间也同步拉长。
4. **错误更隐蔽**。现在答不了的问题会明说"超出能力范围"并落库，失败是诚实的、可统计的；
   动态图倾向于硬答，给出一份"看起来对"但链路是错的分析——对经营决策场景，后者比"我不会"
   危险得多。
5. **对普通商家的风险更高**。动态 DAG 更适合给"专业用户"当工具——程序员、数据分析师这类人有
   判断力，看到"转化率环比 -12%"能本能地察觉数字不对。但我们的用户是普通商家：很多人分不清
   同比、环比，看到一份排版整齐、数字详实的分析，默认它是对的，会据此补货、调价、投流量。
   对普通商家来说，系统输出更接近经营建议，而不是普通工具提示——因此我们更看重"少答但可靠"，
   而不是"多答但不稳定"。

## 4. 什么情况下该重新启用

- 查询能力涨到 50+、场景涨到 8 个以上，手写模板组合爆炸，维护模板的成本超过动态图的
  不确定性成本；
- bad_query_case 聚合出来不是"几个集中的新需求"（集中就该手做成模板），而是**发散的长尾**——
  什么样的问法都有，每种都不多，这时候动态编排才划算；
- 真的出现"绕圈"的需求：多轮追问、边查边修正，直来直去的 DAG 表达不了；
- 启用姿势建议混合式：高频场景继续走模板（稳定、可测），长尾交给动态图兜底，但回答里明确
  标注"这是低置信度的探索性回答"。现有代码已经留了地基：能力目录（capabilities.yaml）就是
  动态编排的工具清单，executor 层原样复用，要换的只是中间那层"谁决定步骤"的引擎。

**即使将来启用，也必须先建好兜底再开放给商家**，可选的兜底手段：

1. **LLM 提案、代码审批**：LLM 生成的执行图先过一道和现在 PlanValidator 同款的机械校验
   （能力在白名单内、依赖合法、引用有出处），校验不过直接不执行——LLM 只有建议权，没有执行权；
2. **数字永不过 LLM 的手**：节点间数值一律用变量引用传递（"把 S1 的 metric_delta 作为输入"），
   LLM 只能传"指向哪个数"，不能亲手抄写数字，从根上断掉抄错数的可能；
3. **结论先过事实校验再返回**：复用现在的 GroundingChecker（数字出处/实体出处/符号一致性），
   校验不过的结论不展示，降级为"这个问题我没能给出可靠结论"；
4. **全程只读**：动态图只允许调查询类能力，物理上不开放任何写操作，错了最多是看错，不会改错；
5. **预算兜底**：限制最大节点数、最大 LLM 调用次数、整体超时——防止动态图绕圈失控、成本爆炸；
6. **灰度开放**：先给内部运营/分析师用（专业用户帮排雷），商家端影子运行一段时间（真实执行但
   结果只记录不展示），通过率达标后再放量；
7. **显著免责与置信度标注**：动态图产出的回答必须带明显标识，如"探索性分析，数字请以经营报表
   为准"，降低商家的默认信任；
8. **降级链**：动态图执行失败或校验不过 → 回退到最近的模板场景 → 再不行就明说超出能力范围。
   永远保住"诚实地说不会"这最后一条路。

## 5. 将来如果要接入，怎么接（落地技术方案）

路由（意图识别输出语义从"准入名单"改为"快速通道"）：

```text
用户问题
  │
  ▼
意图识别
  │
  ├── 命中已知场景
  │     │
  │     ▼
  │   走模板 plan（零不确定性）
  │
  ├── 是经营问题，但没有模板
  │     │
  │     ▼
  │   走动态 DAG 兜底
  │
  └── 明显无关（天气/讲笑话）
        │
        ▼
      返回暂不支持，并记录 bad case
```

执行逻辑（按编号逐步）：

1. **路由**：意图识别照常跑，命中场景枚举（metric_change_diagnosis 等）→ 走模板 plan；枚举外但
   判断为正经经营问题 → 进动态 DAG 通道；明显无关 → 暂不支持话术。动态通道的检索关键字复用
   `suggest_action / suggest_object / suggest_entity / business_intent` 四个结构化字段。
2. **能力检索（RAG——先从能力目录里检索相关能力，再交给 LLM 使用）**：先按
   `suggest_action`/`suggest_object` 对能力目录做结构化硬过滤（要求 capabilities.yaml 给每个
   能力补 description + tags），再用 `business_intent`（LLM 归一化后的意图表述，而非发散的
   用户原文）做向量召回排序，取 top N 作为候选能力集。
3. **LLM 生成 plan**：LLM 在候选能力集内输出执行图 JSON，节点结构与现有 PlanStep 完全一致
   （capability / params / inputs / depends_on），数值一律用 `S1.metric_delta` 式引用，不许抄数字。
4. **静态校验 + repair**：生成的图先过 PlanValidator 同款校验（能力白名单、依赖无环、inputs
   有出处）；不过则把错误明细喂回 LLM 改图（repair 循环，限 2~3 次），改不好直接降级为
   "暂时答不了"。**LLM 只有提案权，执行权在代码。**
5. **代码插入决策点（decision point）**：图校验通过后，代码按规则机械地打"钢印"——如"拆解类
   查询节点后挂'是否继续深挖'的判断点"。决策点的位置由代码预授权，LLM 无权给自己埋决策点
   （否则成本和拓扑都失控）；运行到决策点时 LLM 只做封闭选择题（候选分支是代码预声明的枚举）。
6. **执行**：复用现有 ExecutionService（Kahn 分层并发）与 step_run 落库，一行不改。每步跑完先过
   确定性检查（字段为空/结果集为空/异常，如 hypothesis_broken），再决策点判断是否需要 replan。
7. **replan（运行期调整 plan）**：决策点判定要改图时，新图与当前 run 按**指纹**对比决定存量
   结果的去留——`指纹 = 能力名 + 参数 + 全部上游节点的指纹`（与 Git/审计 hash chain 同理，上游
   变动自动传染下游）。对比结果三种命运：指纹命中 → 复用旧结果；指纹不匹配（自身变了或被上游
   传染）→ 重跑；旧图有而新图不再引用 → 结果正确但无关，留档不喂结论。注意按内容指纹匹配而非
   step_id（重新编号会漂移），结论步（LLM）永不复用。replan 次数设上限，防"改了又改"死循环。
8. **结论与返回**：ConclusionService 生成结论 → GroundingChecker 机械校验 → 通过则带
   "探索性分析，数字以经营报表为准"标识返回；不过则走降级链（回退模板 → 明说不会）。

**优点**：覆盖长尾（"暂不支持"的边界收窄到"没有能力才不答"）、假设证伪可自动换路、能力目录
是唯一起点（加一个能力，动态通道立刻会用，不用写模板）。
**缺点**：LLM 调用次数从 2 次涨到 N 次（生成 + repair + 决策点），成本和延迟同步涨；质量方差
大，依赖校验器和事实校验兜底；可测试性下降（图不固定，断言只能针对约束而非具体结构）。
**业务取舍**：只开放给"枚举外但像正经经营问题"的中间层，头部高频场景永远走模板；商家端必须
先影子运行 + 灰度 + 显著免责标识，专业用户（运营/分析师）先行试用排雷。
