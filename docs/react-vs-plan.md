# 为什么不优先用 ReAct

ReAct（query + 打平的能力列表，LLM 自主决定调用路径）看起来更通用，我们做过对比评估后选择了
模板化 plan，核心原因有四：

**1. 数值传递的确定性。** 经营分析的链路里充满"上一步产出作为下一步参数"的依赖（如
`contribution_ratio` 需要 S1 的 `metric_delta` 做分母）。plan 模式用 `inputs` 声明 + 执行期
`ctx.lookup` 取值，数字不过 LLM 的手；ReAct 模式下 LLM 要从历史 JSON 里"记住"数值再原样填进
下一个调用的参数，四舍五入、张冠李戴都不报错，只是安静地算错——而经营分析的输出全是数。

**2. 成本结构差一个量级。** plan 模式固定 2 次 LLM 调用（意图 + 结论）；ReAct 需要 N 轮
"思考→调用→观察"，每轮携带完整工具列表和不断膨胀的中间结果，token 成本约 5~10 倍，
延迟也从"2 次串行调用 + 毫秒级 SQL"变成十几次串行调用。

**3. 可验证性与可跟踪性。** plan 是执行前的静态产物：PlanValidator 在碰数据库之前就能拒绝
结构非法的 plan（环、能力不存在、inputs 无着落），plan 结构可打印、可 diff、可写单测断言
（见 `PlanWeaverTest`）。ReAct 的轨迹是概率性的，校验只能是执行后的事后审计，且"缺失某步"
这类错误在事后最难定义；跟踪一个每次运行都不同的十几轮 trace，和跟踪一个九行的 plan 对象，
是两个量级的成本。

**4. 质量分布。** 即便 ReAct 有不低的概率走出和 plan 相同的路径，它每次仍落在质量光谱的不同
位置（步骤缺环、顺序混乱、数值传错但结论"看起来对"）。plan 模式把"选对路径"从运行时的概率
事件提前为设计时的确定性决策，方差为零。

## ReAct 的真实优势（当前方案的边界）

- **覆盖面**：骨架之外的 query（如"新客老客占比变化"）plan 模式答不了或硬塞进错误场景，
  ReAct 至少能摸出一条合理路径；
- **免模板工程税**：加能力不用设计骨架/因子 YAML；
- **中途自我纠正**：假设证伪后换思路是 LLM 的天然能力，而我们用 `hypothesis_broken` 规则
  硬编码了一种。

## 适用边界与演进路线

经营分析是高度套路化的领域（指标诊断/查询/因子评估覆盖绝大多数真实查询），能力 <20、
场景 <5 时 plan 模式全面占优；能力 50+、长尾查询占比高时，ReAct 或"LLM 生成 plan 再校验执行"
（plan-and-execute）才开始划算。务实的混合方案：意图识别命中已知场景走确定性 plan，
置信度低或未命中时降级 ReAct 兜底。
