# Playbook 与 ReAct 如何配合

当前已采用混合架构：固定流程可覆盖时走 Playbook；其余领域内问题走 ReAct，并可用文字场景指导。这里不再沿用旧版“为什么不使用 ReAct”的结论。

| 方面 | Playbook | 当前 ReAct |
|---|---|---|
| 选择步骤 | 骨架 + 因子，运行前确定 | 模型按实际结果逐轮决定 |
| 主要适用 | 高频、稳定、可配置的固定业务路线 | 多实体、动态商品集合、组合查询、模板外需求 |
| 业务指引 | YAML 节点/依赖 + 因子 MD | 可选场景 YAML 中的一段 guidance |
| 数据传递 | inputs 转结构化引用 | 参数显式 `$ref` 引用 |
| 校验时机 | 启动 + 完整 Plan 运行前 + 工具调用时 | 每次动作/工具调用 + finish 完成度检查 |
| 模型次数 | 通常理解和结论 2 次 | 默认最多 12 次 ReAct 调用，另有前置理解 |
| 工具定义 | 执行时按定义使用 | 初始只见摘要，完整接口按需加载 |
| 循环控制 | DAG 无环、有限节点；证伪只跳过模块后续 | 次数、时限、缓存、无进展、重复错误、上下文上限 |
| 恢复 | 原 Plan + 成功步骤 | 原动态状态 + 原预算/截止时刻 + 已有事实 |

两条路径的数字都可以通过代码引用传递，不能再说“ReAct 必须让模型记住并抄写所有数值”。两条路径都依赖 LLM 理解和回答，因此模板不意味着端到端质量方差为零。也没有本轮真实模型实验支持固定的成本倍数；预算是约束，不是性能或效果测量。

## 选择原则

覆盖判断依据 requirements 的 action、metric、scope、实体、因子和时间，不只看场景名称。不可把原问题改窄以命中模板，也不因未命中文字场景就拒答。

有固定流程时，Playbook 更易预先审查路线和依赖；文字经验可描述但不适合固定编排时，ReAct 场景可减少随意探索。两者都不能替代缺少的数据、工具、权限和业务定义。多加一段场景说明不能让系统突然计算复购、预测或因果损失。

## 如何继续演进

观察实际 trace 中的完成度、缺失能力、无进展次数和真实模型成本，再决定是否新增文字场景或固化 Playbook。当前 bad_query_case 只自动收集领域外和 CAPABILITY_MISSING，不包含全部 ReAct 成功/部分轨迹；要做覆盖率分析还需要关联 analysis_run/react_run/react_event，不能只读 bad_query_case 推断全量效果。

具体实现见[路由](routing-and-query-rewrite.md)、[工具](tools-and-calculations.md)、[ReAct](react.md)。
