# 会话与追问实现细节

README 中只保留了用户视角的追问能力说明，本文档记录实现细节：memory 定位、会话找回、存储结构、run chain、追问判定与分类处理。

## 定位：memory 只做会话上下文

这里的 memory 只用于保存会话上下文，帮助系统理解用户是不是在追问；不会保存用户画像、社交关系等个人长期记忆。目标是让系统在用户追问时知道他接着哪一次分析在问；即使过两天回来，也能继续同一个话题。

## 会话找回

请求中可以带 `sessionId`，表示用户明确选择了某个历史会话继续提问；如果没有传 `sessionId`，系统会默认查找该用户最近 7 天内的活跃会话，作为可能的上下文；无活跃会话（首次访问）则不注入任何历史、直接开新会话。会话按 `merchantId + userId` 隔离，同一家店铺下，不同运营人员之间看不到彼此的会话记录。

## 存储结构

会话相关的数据主要存两张表：`conversation_session`（会话入口）、`conversation_turn`（每轮问答）。`run_id` 表示本轮新产生的分析任务；`ref_run_id` 表示本轮回答引用的是哪一次历史分析。对于需要重跑的追问，本轮会产生新的 `run_id`，同时通过 `root_run_id` 挂到原话题链上；对于不需要重跑的追问，本轮通常不产生新的分析任务，只记录 `ref_run_id`，表示回答基于哪次历史分析结果生成。

## run chain

同一个话题下的多次分析记录通过 `analysis_run.root_run_id` 关联在一起（首问的分析任务为链根，追问重跑的新任务挂到链根下），负责归属与追溯。简单来说，`conversation_session / conversation_turn` 负责保存用户对话，`analysis_run.root_run_id` 负责保存同一分析话题下的任务链路，`turn.run_id / turn.ref_run_id` 用来把一轮对话和对应的分析任务或历史分析结果关联起来。

判断用户是否在追问时，系统会参考该用户最近两个话题的最新一轮分析，包括分析记录、识别出的意图和上一轮结论。这里限制候选数量，是为了控制 prompt 长度，并降低把新问题误判成历史追问的概率。

## 追问判定并入意图识别

是否为追问，会在意图识别这一次 LLM 调用里一起完成，不会额外调用 LLM。意图识别时，系统会注入最近可参考的历史分析。LLM 需要判断：是否为追问、属于哪种追问类型、引用哪次历史分析（`ref_run_id`）、是否需要重新查询数据，并输出补全后的结构化意图。

如果是追问，系统会默认沿用上一轮分析中的指标、时间、商品等信息，只替换用户本次明确修改的部分——例如用户只问"那订单量呢？"，系统会沿用上一轮的时间范围和对比基准，只把指标从销售额替换为订单量。

如果 LLM 判断这是追问，但返回的 `ref_run_id` 不在本次注入的候选历史分析范围内，系统会拒绝该引用，并把本次请求当作一个全新的问题处理。

## 追问分类与处理方式

追问按处理方式分为两大类：需要重跑的追问，以及可以复用历史结果直接回答的追问：

| 追问类型 | 例子 | 处理 |
|---|---|---|
| 更换指标 / 更换对比时间（metric_switch / time_compare） | 用户先问"上个月销售额为什么下降？"，再追问"那订单量呢？"或"那跟前两个月比呢？" | 重跑：换指标/时间走正常链路，新的分析任务挂到原链 |
| 追问原因细节 / 追问建议 / 追问解释（factor_detail / advice / explain） | 用户先问"销售额下滑跟无糖可乐下架有关吗？"，再追问"下架影响到底多大？"或"那我该怎么办？" | 不重跑数据：引用被承接任务的结论与步骤结果，调用结论生成 LLM 组织回答，并保存 `turn.answer` |
